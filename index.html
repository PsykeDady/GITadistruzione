Comprendere GIT

- `Git` è abbastanza banale da usare nelle operazioni quotidiane, ma è prima necessario comprendere la struttura su cui è basato. - È un sistema di controllo delle versioni distribuito; - Git salva delle snapshot (blob binari ) dello stato del progetto, organizza i dati in oggetti e pacchetti compressi, utilizzando anche meccanismi di compressione a delta (ovvero memorizzando solo le differenze tra le versioni) per ottimizzare lo spazio.
Git prevede 3 stati di memorizzazione per i file: - **Working directory**: dove modifichiamo e creiamo i file. - **Staging area (index)**: dove selezioniamo le modifiche da includere nel prossimo commit. - **Repository locale**: dove Git salva uno snapshot permanente del progetto. - **Repository remoto**: dove i commit possono essere inviati per la condivisione e la collaborazione.
![Working staging repo base](assets/working-staging-repo_base.png)
![la struttura delle directory git](/assets/WorkVSStageVSRepo.png)
Quando si punta ad un *repository remoto*, gli scambi di codici con quello locale son detti: - operazione di **pull**, se in download da remoto a locale. - operazione di **push**, se in upload da locale a remoto.
### Remoto? - Nel caso di Git, "remoto" è una parola un po’ fuorviante. - Git può collegarsi ad un altro repository tramite un URL e scambiarsi commit, integrando le rispettive storie del progetto. - L’URL può essere sia una cartella locale, sia un indirizzo di rete (server, GitHub, ecc.). - Questo permette, ad esempio, di sincronizzare i progetti anche tramite una cloud dati.

Git ignore

- non tutti i file di un progetto devono essere tracciati da git - è il caso di file di configurazione locali, file generati da build etc... - La soluzione è il **gitignore**.
- Il file `.gitignore` è un file di testo che contiene una lista di pattern che indicano quali file o cartelle devono essere ignorati da git. - I pattern possono essere specifici (es. `config.json`) o generici (es. `*.log` per ignorare tutti i file con estensione .log). - Il file `.gitignore` deve essere posizionato nella root del repository e deve essere tracciato da git (ovvero deve essere incluso nei commit) per essere efficace. - Se da un percorso escluso vuoi reincludere un file specifico utilizza `!percorso/file` (es. `!config/config.json` per reincludere il file config.json nella cartella config).
```plain # Ignora tutti i file con estensione .log *.log # Ignora la cartella build target/ # Ignora i class *.class # Ignora le properties di eclipse .project/ # Reincludi un file da project !.project/config.json ```
- Esistono dei siti come gitignore.io che permettono di generare dei file .gitignore precompilati per diversi linguaggi e framework. - Un altro progetto interessante è https://github.com/janniks/git-ignore che permette di generare dei file .gitignore direttamente da terminale.

Operazioni base

- `git status` per vedere lo stato del repository - `git add [file]` per aggiungere i file alla staging area - `git add .` per aggiungere tutti i file modificati alla staging area - `git commit` per creare un commit con i file nella staging area - `git commit percorso/file` per creare un commit con uno o più file specifici - `git commit -m "messaggio"` per creare un commit con un messaggio specifico
### rimozione modifiche - `git checkout -- [file]` per annullare le modifiche a un file (riporta il file alla versione dell'ultimo commit) - `git reset --hard` per annullare tutte le modifiche - `git clean -xdf` per rimuovere i file non tracciati - `git commit --amend` per modificare l'ultimo commit - `git revert [commit]` per annullare un commit specifico (crea un nuovo commit che annulla le modifiche del commit specificato)
### Rimozione file ignorato - Se un file tracciato da git viene aggiunto al .gitignore le sue modifiche non verranno più tracciate - Ma il file continuerà ad esistere nel repository. - Se lo si vuole rimuovere completamente è necessario utilizzare `git rm --cached [file]` e committare.
### Buone pratiche - Fare commit frequenti e con messaggi chiari - add molto specifici (evitare `git add .` se non si è sicuri di voler includere tutte le modifiche) ### Trivia: what the commit ```bash git commit -m "$(curl -s https://whatthecommit.com/index.txt)" ```
- `git log` per vedere la storia dei commit - `git log --oneline` per vedere la storia dei commit linea per linea - il log restituisce i sha del commit, che sono identificatori univoci per ogni commit - utili per revert, cherry-pick, ecc.
- commit aaaa123 - aggiunto file 1 - commit bbbb321 - aggiunto file 2 - commit c1aab12 - modificato file 1 Digitando: ```bash git revert bbbb321 ``` si ritornerà alla situazione in cui ancora *non è stato aggiunto il file 2*, ma in cui è ancora valido il **commit aaaa123**. Se si aggiunge il parametro **-n** è possibile evitare il commit: ```bash git revert -n codicecommit ```
- Per andare dal commit alla staging area ci son due metodi - dal secondo commit in poi: `git reset --soft HEAD^` - Nel caso del primo commit: `git update-ref -d HEAD`

Comunicare con remote

- Se si ha impostato almeno un repository remoto, è possibile comunicare con esso tramite i comandi `fetch`, `pull` e `push`. - A differenza di `pull` e `push`, `fetch` scarica solo i cambiamenti senza applicarli automaticamente. - `pull` scarica i cambiamenti e li applica automaticamente al branch corrente - mentre `push` carica i cambiamenti dal branch locale a quello remoto.
- in fase di comunicazione con un repository remoto è possibile incorrere in *conflitti*, se nel frattempo altri utenti hanno effettuato modifiche. - La maggior parte dei conflitti git riesce a risolverli automaticamente (in fase di `pull`). - Senza un'adeguata strategia di merging, in fase di `pull` è necessario specificarla manualmente. - `git pull --ff` ad esempio applica il fast forward e lascia gestire i conflitti più complessi all'utente. - non è possibile fare `push` se nel frattempo altri utenti hanno fatto modifiche, è necessario prima fare `pull`, risolvere eventuali conflitti e poi fare `push`.

Branch

- Lavorare bene con git significa anche saper gestire i branch, ovvero le linee di sviluppo parallele all'interno del progetto. - I branch permettono di lavorare su funzionalità o bugfix in modo isolato
- `git branch` per vedere i branch esistenti - `git branch nomebranch` per creare un nuovo branch - `git checkout nomebranch` per spostarsi su un branch esistente - `git checkout -b nomebranch` per creare e spostarsi su un nuovo branch - `git branch -D nomebranch` per eliminare un branch
![Branching](assets/branch.png)
### Tag vs Branch - `git tag nometag` per creare un nuovo tag - i tag sono come i branch, ma non si spostano, sono fissi su un commit specifico - i tag sono spesso usati per segnare le release del progetto - i branch sono invece usati per lo sviluppo continuo
### Push pull tag e branch - `git push origin nomebranch` per pushare un branch su remoto - aggiungi `--set-upstream` per impostare il tracking del branch remoto - `git push origin nometag` per pushare un tag su remoto - `git push -d origin nomebranchotag` per eliminare un branch o un tag su remoto

Branch Strategy

- Esistono delle convenzioni per la gestione dei branch. - Gestire adeguatamente i branch aiuta lo sviluppi e la coordinazione tra i membri del team, soprattutto in progetti di grandi dimensioni. - Alcuni strumenti riescono a gestire in autonomamente le versioni se presente una strategia di branching ben definita (es. GitFlow, GitHub Flow, ecc.).
- `main` o `master`: branch principale, stabile, pronto per la produzione - `develop`: branch di sviluppo, dove vengono integrate le nuove funzionalità prima - `feature/nomefeature`: branch per lo sviluppo di una nuova funzionalità - `hotfix/versione`: branch per la correzione di un bug critico - `release/versione`: branch per la preparazione di una nuova release - `support/versione`: branch per la manutenzione di una vecchia versione
- `master` non si usa più, è stato sostituito da `main` per evitare connotazioni razziste - Coordinati sempre con chi gestisce il team - Alcuni sistemi permettono di bloccare il push su branch specifici (es. `main`) per evitare di fare modifiche direttamente su di essi - La branch strategy va di pari passo con la numerazione delle release in genere. - main → major (`1.0.0`), develop → minor (`1.1.0`), hotfix/release/support → patch (`1.1.1`)
- Strumenti come gitflow aiutano a gestire il versionamento del progetto - Gitflow è generalmente utilizzato attraverso plugin maven e permette di fare build e avanzamenti in contemporanea - `mvn gitflow:release-start` per iniziare una nuova release - `mvn gitflow:release-finish` per terminarla - Il pom deve contenere la branch strategy per funzionare correttamente

Merge/Rebase

- Quando si stacca un branch si crea una copia del progetto nello stato attuale del branch da cui si stacca. - Dal momento in cui si fanno modifiche nel nuovo branch la storia diverge. - Anche il branch originale può subire modifiche, creando ulteriori divergenze. - Per riconciliare le divergenze tra i branch esistono due operazioni principali: `merge` e `rebase`.
- Il `merge` crea un nuovo commit che unisce le modifiche dei due branch, mantenendo la storia di entrambi i branch - Il `rebase` riallinea il branch nuovo alla storia di quello originale. - Il `rebase` può anche essere usato per allineare il branch staccato sulla storia di un altro branch, come se si fosse generato originariamente da li.
- Spesso `merge` e `rebase` vengono confusi o usati "al contrario" (rebase non viene usato spesso). - È certo importante usarli con la logica corretta. - Ma ci son casi in cui, effettivamente, il `merge` è più comodo rispetto al `rebase` (che crea più conflitti)
- Per usare `merge` bisogna essere sul branch originale e digitare `git merge nomebranchdaincludere` ```sh git checkout main git merge feature/nuovafunzionalità ``` - Il `rebase` si usa al contrario, bisogna essere sul branch staccato e digitare `git rebase nomebranchoriginale` ```sh git checkout feature/nuovafunzionalità git rebase main ```
- In alcuni casi i conflitti vengono reiterati più volte (caso `rebase`) - `git rebase --continue` per continuare l'operazione dopo aver risolto un conflitto - Se qualcosa non convince l'operazione è possibile annullare l'operazione - `git merge --abort` per annullare un merge in caso di conflitti - `git rebase --abort` per annullare un rebase in caso di conflitti - Gli IDE o i strumenti esterni risolvono i conflitti in modo più semplice.
- Generalmente git risolve automaticamente i conflitti con il fast forward. - Per essere sicuri di non generare conflitti irrisolvibili da git, non c'è bisogno di lavorare su file diversi. - non lavorare sulle stesse righe (un ottima tecnica è dividersi il file a metà)
### Merge o pull request - le piattaforme di hosting remoto (Github, Gitlab, etc...), offrono diverse operazioni - le pull/merge request ad esempio che permettono di gestire la riconciliazione tra due branch - Su repo su cui non si hanno diritti, per generare una PR è necessario fare un fork del repository, creare un branch sul proprio repository, fare le modifiche e poi generare una PR verso il repository originale.

Stash

Diff e patch

I submodule di git

- I submodule di Git permettono di includere un repository Git all'interno di un altro repository. - Sono utili quando si vuole integrare una libreria o un progetto esterno mantenendolo separato. - Il repository principale non copia il codice del submodule, ma mantiene un riferimento ad uno specifico commit di quel progetto. - `git submodule add URL` per aggiungere un submodule - `git submodule update --init` per inizializzarlo
- Se il progetto principale si aggiorna, il submodule non viene modificato automaticamente: rimane fermo al commit registrato. - Questo garantisce stabilità e controllo sulle versioni. - Se invece è necessario modificare realmente il submodule, si può entrare nella sua directory, fare commit e push come in un repository normale, e poi aggiornare il riferimento nel progetto principale.
```sh # Aggiunge un repository esterno come submodule git submodule add URL percorso/del/submodule # Registra il submodule nel progetto principale git commit -m "Aggiunto submodule libreria" # Inizializza e scarica i submodule git submodule update --init # Aggiorna il submodule al commit più recente del branch configurato git submodule update --remote # Registra il nuovo riferimento nel progetto principale git add libs/libreria git commit -m "Aggiornato submodule" # Entrare nella directory del submodule cd libs/libreria # Lavorare normalmente (add, commit, push) git add . git commit -m "Modifica nel submodule" git push # Tornare nel progetto principale cd ../.. # Aggiornare il riferimento al nuovo commit git add libs/libreria git commit -m "Aggiornato riferimento submodule" ```
